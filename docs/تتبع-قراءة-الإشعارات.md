# تتبع قراءة الإشعارات + التفعيل التلقائي — ما يلزم من تطبيق تَحَكَّم والـ worker

اللوحة جاهزة بالكامل من جهتها. هذه الوثيقة تشرح **التغييرات الصغيرة المطلوبة في ريبو `shopsys`**
(التطبيق + `tools/devbot/src/worker.js`) حتى تعمل خاصيتان من طرف العميل.

---

## 1) «من قرأ الإشعار؟» — إيصالات القراءة

### ما تعرضه اللوحة الآن (حتى بدون أي تغيير)
| الحالة | المصدر |
|---|---|
| ✅ **قرأه** | إيصال في `noticeread:<deviceId>` (يحتاج التغيير أدناه) |
| 📥 **وصله** | `dev:<deviceId>.lastSeenAt` أحدث من وقت الإرسال — أي فتح التطبيق وجلب الإشعارات بعده |
| ⏳ **لم يصله** | لم يتصل التطبيق منذ الإرسال |

> «وصله» يعتمد على ختم `lastSeenAt` (Phase 0 في خطة اللوحة): عند كل
> `GET /subscription/:deviceId` و`GET /notifications/:deviceId` يُحدَّث `dev:<deviceId>.lastSeenAt`.

### العقد المطلوب للإيصالات
**في التطبيق:** عند فتح العميل للإشعار (أو عرضه على الشاشة) يرسل:
```
POST /notifications/:deviceId/read
{ "ids": ["<noticeId>", ...] }
```

**في الـ worker** (مساحة `SHOPSYS_CONTROL` — نفس مكان `notices:*`):
```js
// noticeread:<deviceId> → { "<noticeId>": "<ISO وقت القراءة>" }
const key = `noticeread:${deviceId}`
const cur = JSON.parse(await env.SHOPSYS_CONTROL.get(key) || '{}')
const now = new Date().toISOString()
for (const id of body.ids.slice(0, 50)) if (typeof id === 'string' && !cur[id]) cur[id] = now
// إبقاء آخر 200 إيصال فقط
const trimmed = Object.fromEntries(Object.entries(cur).sort((a, b) => a[1].localeCompare(b[1])).slice(-200))
await env.SHOPSYS_CONTROL.put(key, JSON.stringify(trimmed))
```
اللوحة تقبل أيضاً الشكلين `["id1","id2"]` و`[{ "id": "...", "at": "..." }]`.

### تعديل وحذف الإشعارات
- **التعديل** يحافظ على نفس `id` ويضيف `editedAt` — التطبيق يعرض النص الجديد في أول مزامنة
  (يُفضَّل أن يعيد التطبيق عرض الإشعار كـ«غير مقروء» لو تغيّر `editedAt`).
- **الحذف** يزيل الإشعار من `notices:global` / `notices:<deviceId>` — يختفي عند أول مزامنة
  ما دام التطبيق لا يحتفظ بنسخة محلية من إشعارات حُذفت من السحابة.

## 2) التفعيل التلقائي بدون أن يلصق العميل المفتاح

### الوضع الحالي
- **الباقة وتاريخ الانتهاء** تُكتب في `sub:<deviceId>` (مساحة الخدمات) ويقرؤها التطبيق من `/subscription`.
- **الأقسام والميزات والنشاط** داخل المفتاح الموقّع — لذلك يجب أن يُدخل العميل المفتاح الجديد.
  اللوحة توفّر زر **«📨 أرسل المفتاح للعميل داخل التطبيق»** فيصله في إشعاراته.

### ما أضافته اللوحة للتفعيل التلقائي
عند كل إصدار تكتب اللوحة الآن المفتاح نفسه في بطاقة الاشتراك:
```json
sub:<deviceId> → { "plan": "...", "expiresAt": "...", "customer": "...", "issuedAt": "...", "key": "SHOPSYS1....", "fingerprint": "abcd1234" }
```
**المطلوب في التطبيق:** عند المزامنة مع `/subscription`، لو احتوى الرد على `key` مختلف عن المفتاح
المحفوظ → `verifyLicenseKey(key, deviceId)` ثم حفظه. التحقق نفسه يضمن الأمان: المفتاح موقّع،
ومربوط بمعرّف الجهاز، فلا قيمة له لأي جهاز آخر حتى لو قرأه أحد.

---

## 3) أسئلة متكررة عن المفتاح (من كود التحقق `verifyLicenseKey`)
- **مربوط بالجهاز؟** نعم — `deviceId` جزء من الحمولة الموقّعة، والتطبيق يرفض المفتاح لو اختلف المعرّف.
- **يُحرق بعد الاستخدام؟** لا — صالح على نفس الجهاز حتى `expiresAt` أو حتى يُضاف إلى قائمة `revoked`.
- **إصدار مفتاح جديد يُبطل القديم؟** لا تلقائياً — خيار «حرق المفتاح السابق» في نموذج الإصدار، أو «تعطيل» من بطاقة العميل.
- **تكرار الأقسام؟** المفتاح الجديد يحلّ محل القديم بالكامل (`extraModules` قائمة كاملة لا إضافة)،
  واللوحة تزيل التكرار وتخفي أقسام النشاط والأقسام الموجودة قبل التوقيع.
